# ProbePlanner v0.3.0-paper

Source and evidence record for `v0.3.0-paper`. Publication is determined by the
release page and final validation report, not by the presence of these notes in
a candidate branch. Draft assets are not a completed public release.

## Relationship To Earlier Releases

This is the post-review corrected-source paper revision after `v0.2.1-paper`,
which was the corrected final-source release after `v0.2.0-paper`. Neither old
tag is moved or replaced. Repairs made in response to observed failures remain
post-hoc repairs, not untouched evidence.

The unchanged historical archive preserves:

- The first v4 execution: 16 positive full, three partial and one expected
  fail-closed outcome. Its failed gate remains visible.
- The explicitly labelled post-hoc remediation.
- The later frozen v5 confirmation: 19/19 positive full and strict, 1/1 expected
  negative fail-closed, zero partials or errors.
- The v5 exact comparison: 19/19 certified candidate-pool minima and 19/19 planner
  count matches, zero timeouts.
- The historical exact regression: 48/48 certified minima and count matches,
  zero timeouts.

These historical certificates are not assigned to newly generated candidate pools.

## Revised Source And Its Evidence

The revised implementation incorporates post-review corrections to segment
distance/collision handling, atlas-coordinate proposal generation and consistent
trajectory serialization/contact geometry. It exposes bounded token-cover
completion, uses the explicit verified-profile Python startup, and improves
registration-evidence availability, audit interfaces and actual UI inspection.
The legacy antivirus-deleted launcher remains absent and is not whitelisted.

The repaired source was evaluated by full candidate regeneration with separately
recorded independent geometry audits, finite-pool exact models and same-pool
comparators:

- Retrospective replay: 89/89 positive full and strict, 9/9 expected negative
  fail-closed, 89/89 valid exact count matches, zero partials/errors/timeouts.
- Subsequent separately frozen request confirmation: 12/12 positive full and
  strict, one reused negative correctly fail-closed, 12/12 exact count matches,
  zero partials/errors/timeouts.
- Same-pool comparisons: 2,492 retrospective and 336 confirmation evaluations.
  These include incomplete and collision-producing comparator outcomes; they are
  not all described as successful plans. Twenty random seeds are not independent
  biological replicates.

The original 112-test subset is retained as an exact-count gate. The complete
backend suite contains 329 tests, including that subset. Frontend verification
contains 152 tests; optional surface construction has six tests. Packaging tests
are separately reported. Final run counts and hashes must be taken from the
new release report, not inferred from these suite descriptions.

## Reproduction And Data

The [reproduction guide](v0.3.0-reproduction.md) describes actual startup, pinned
profile downloads, archived-model verification and complete candidate regeneration.
Public evidence is a separately hashed, independently checked path-only projection;
it is not a rewritten original frozen manifest. Requests, models and protected
scientific outcomes retain their original bytes.

The public profile retains the evaluated scientific arrays and meshes byte for
byte. Path metadata and its hashes are explicitly derived. AMBMC and Allen data
have their own notices and licensing conditions; the software MIT license does
not relicense those data. Missing moving-mask/full MRI application-chain evidence
is not reconstructed by packaging or by the public atlas identity checks.

The version-specific workflow validates an explicit candidate commit against
staged draft assets and contains no publishing command. Only the isolated asset
download job has push-level permission to access drafts; source execution uses
read-only permissions. The annotated release tag is fixed after CI passes.
Public HTTPS download verification, a fixed clean commit and annotated tag, and
the real Zenodo version record remain distinct release steps.

## Supported Scope

The release supports auditable software behavior and exact minimum cardinality
within each regenerated, strictly filtered finite candidate pool. The separately
packaged Rust engine is not the Python paper-validation runtime and is not
revalidated by substituting its version string.

It does not establish continuous-space global optimality, subject-specific TRE,
bregma/lambda accuracy, native-space surgical safety or histological implantation
accuracy. Public population-template geometry is not a subject-specific skull or
anatomical landmark measurement.
