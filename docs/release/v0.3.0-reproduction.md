# Reproducing the revised paper runtime

The commands below implement the reproducible route. Use the matching published
release's assets and reports; a candidate branch does not imply that its tag,
public assets or Version DOI already exist.

## Inputs And Environment

Use the evaluated Python planner, not the independent Rust engine. Install
`apps/backend-compat/requirements-lock-py310.txt` in a fresh Python 3.10 environment.
For optional offline mesh building and its six tests, install the separate
`apps/backend-compat/requirements-surface-build.txt` lock in another environment.
The runtime does not import VTK. Install JavaScript dependencies with `npm ci`
and `npm --prefix apps/ui ci` from the checked-out source.

Place `PUBLIC_VALIDATION_EVIDENCE.zip` and `PUBLIC_EVIDENCE_MANIFEST.json` together
in `EVIDENCE_DIR`. The manifest SHA-256 is
`ff539dcc0781061acd4a8d15f0e2b3d1fc8d66d1eb2c603db2d5f142b3e614a2`.
The evidence verifier pins this identity internally.

The runtime data consist of the four `ProbePlanner-v0.3.0-paper-profile-*.zip`
assets and `DATA_BUNDLE_MANIFEST.json`. The bundle manifest SHA-256 is
`f3ab8b854a6f665ad484ea7ae95c41d6212fafb92099044949ec84cec171ad9a`.
Replace `ASSET_BASE_URL` with the release's HTTPS asset-directory URL and the
uppercase path placeholders with actual paths:

```sh
python scripts/release/fetch_public_profile.py \
  --base-url ASSET_BASE_URL \
  --manifest-sha256 f3ab8b854a6f665ad484ea7ae95c41d6212fafb92099044949ec84cec171ad9a \
  --downloads NEW_DOWNLOAD_DIR --profile NEW_PROFILE_DIR --report NEW_DOWNLOAD_REPORT.json
```

Download and output directories must not already exist. The fetcher verifies
every asset and extracted member before accepting the profile. Its contract
SHA-256 is `3580f40eb42b475319ea62796ef8c7b8789b1d1110a9ca4638f8e2168b09c677`.
The original evaluated profile is retained under a different identity; path-only
public derivation does not change scientific file bytes or upgrade MRI evidence.
See [data notices](data/DATA_NOTICES.md) for the distinct data licenses.

## Actual Runtime

```sh
npm --prefix apps/ui run build
python apps/backend-compat/scripts/start_paper_backend.py \
  --profile NEW_PROFILE_DIR --run-dir NEW_RUNTIME_DIR \
  --static-dir apps/ui/build --port 5039
```

Open `http://127.0.0.1:5039`. Runtime identity is exposed by `/api/paper/runtime`.
For a cold-start check without an HTTP listener, omit `--static-dir` and add
`--check-only`. Existing run directories and occupied ports are rejected.

## Candidate Generation, Independent Audits And Exact Models

The portable runner stages six byte-preserved scientific campaign modules from
the pinned evidence archive. It replaces only the machine-path binding module
with an explicit local configuration. The archived oracle and required historical
models come from the unchanged older release archive in the source checkout.
It does not call the obsolete machine-specific campaign entry points.

For the fixed three-case packaging smoke:

```sh
python scripts/release/replay_public_campaign.py \
  --evidence-dir EVIDENCE_DIR --profile NEW_PROFILE_DIR --output NEW_REPLAY_DIR \
  --case retrospective/search_unilateral_ca1 \
  --case confirmation/independent_request_01 \
  --case confirmation/reused_negative_control
```

Each positive makes one actual pipeline call, independently audits individual
candidates and all model pairs, rebuilds the finite-pool exact model, runs the
bounded MILP worker, and repeats 28 same-pool comparator evaluations. The gate
compares candidate/selected geometry and target data, the complete mathematical
model, exact counts and comparator outcomes with the archived run. Runtime/path
metadata and gzip timestamps are not numerical outcomes. The negative must retain
its expected fail-closed code. Errors and failed outcomes remain in the new output;
the runner does not retry or replace cases.

To reproduce all recorded requests, omit all `--case` options. The default then
runs both cohorts, keeping them separate: 98 retrospective requests (89 positive,
nine negative) and 13 confirmation requests (12 positive, one reused negative).
Use `--cohort retrospective` or `--cohort confirmation` to select one complete
cohort. Full replay can be substantially slower than the smoke; do not interpret
these repeated inputs as new untouched validation or independent animals.

The actual public-profile portability smoke passed all three cases. This is
separate from the already retained full-cohort scientific runs. A new full public-
profile replay has not been represented as completed by that three-case smoke.

## Local Release Checks

```sh
python scripts/release/run_release_checks_v030.py \
  --evidence-dir EVIDENCE_DIR --profile NEW_PROFILE_DIR --replay-dir NEW_REPLAY_DIR \
  --surface-python SURFACE_ENV_PYTHON --output NEW_CHECKS_DIR
```

The release checker requires the three fixed replay cases above. It rechecks
their files, verifies source/profile identity, runs the unchanged original
112-test subset and complete 329-test backend suite, the six optional mesh-builder
tests, packaging tests, 152 frontend tests, frontend lint/build, and re-solves
the old 19/48 and current 89/12 exact models. Counts overlap and are not summed.
Any failure or original-subset count other than 112 stops the gate. The only
permitted skip is the identified Windows unprivileged-symlink packaging fixture;
it is not permitted in the original subset, backend or frontend suites.

Candidate CI uses `--require-clean` against an explicit commit SHA before the
release tag is created. Final tag verification additionally uses
`--require-clean --tag v0.3.0-paper`. The local report is not a public-endpoint
check or a DOI. GitHub's v0.3.0 workflow is manually dispatched on the candidate
ref with `source_commit` equal to its full SHA. An isolated job downloads draft
assets with the push-level permission GitHub requires for drafts; it never checks
out or executes candidate source. The verification job uses read-only repository
permissions. Neither new job contains a publishing command. The historical tag
job and verifier remain separate, and old tags must not be moved.

Exactness concerns only each regenerated strictly filtered finite candidate pool.
These checks do not establish continuous-space global optimality, subject-specific
TRE, skull-landmark accuracy, native-space surgical safety or implantation accuracy.
